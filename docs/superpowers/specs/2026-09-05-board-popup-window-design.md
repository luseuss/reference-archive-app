# 무드보드 팝업 창 — 설계

- 작성일: 2026-09-05
- 상태: 브레인스토밍 완료, 사용자 검토 대기
- 관련: `CLAUDE.md` "무드보드 추가 제안 → 우선순위 높음 → 무드보드를 진짜
  별도 창(팝업)으로 띄우기", 2026-08-31 스파이크 기록

## 배경

지금 "항상 위"(PR #30, `board_window_controller.dart`)는 **메인 창 하나를
다른 프로그램 위로 띄우는 것**입니다. 의뢰인이 원하는 것은 다릅니다 —
메인 창에서 레퍼런스 정리 같은 다른 작업을 계속하면서, **무드보드만
따로 떼어 옆에 띄워두는 것**입니다(스크린샷: 옛 웹앱이 브라우저
Document PiP API로 이미 이렇게 동작했습니다).

2026-08-31에 `desktop_multi_window` 패키지로 스파이크를 떠서 "진짜 두
번째 OS 창을 띄울 수 있다"와 "그 창이 같은 sqlite 파일에 별도 연결을
열어도 문제없이 읽는다"까지는 확인해뒀습니다(코드는 버렸습니다).
이번이 그걸 정식으로 만드는 작업입니다.

## 범위

**이번 스펙은 "메인 창에서 열어둔 판 하나를 팝업 창으로 뽑아내기"만
다룹니다.** 목록 화면에서 새 무드보드를 팝업으로 바로 여는 것,
여러 팝업을 동시에 띄우는 것은 다루지 않습니다(아래 "결정된 것" 참고).

## 결정된 것 (브레인스토밍 중 사용자에게 직접 확인)

1. **팝업 창이 보여줄 판**: 지금 메인 창에서 열려 있는 판 하나입니다.
   목록에서 아무 판이나 골라 팝업으로 여는 기능은 이번에 포함하지
   않습니다.
2. **팝업은 한 번에 하나만.** 이미 팝업이 떠 있는 상태에서 다시
   "팝업으로 띄우기"를 누르면, 새로 열지 않고 **있던 팝업이 다른
   판을 보여주도록 바꿉니다**(창을 여러 개 겹쳐 관리하게 만들지
   않기 위함).
3. **메인 창을 닫으면 팝업도 같이 닫힙니다.** 메인 창이 앱의
   진입점이라, 그것이 사라지면 데이터베이스 연결도 정리해야 더
   안전합니다.
4. **두 창 사이는 실시간으로 동기화됩니다.** 한쪽에서 카드를 옮기면
   다른 쪽에도 바로 반영됩니다. drift의 자동 갱신(`watch()`)은 같은
   프로세스의 같은 연결 안에서만 작동하고 두 창은 서로 다른 연결이라,
   **저장할 때마다 상대 창에 "다시 읽어라"는 신호를 명시적으로
   보내야** 합니다(아래 "실시간 동기화" 참고).

## 아키텍처

### 창 두 개, 같은 프로세스

`desktop_multi_window` 패키지는 완전히 별도의 앱 인스턴스를 띄우는 것이
아니라, **같은 프로세스 안에서 Flutter 엔진을 하나 더 띄우는 방식**입니다
(스파이크로 확인됨). 그래서 "메인 창을 닫으면 팝업도 같이 닫힌다"는
요구가 자연스럽게 풀립니다 — 메인 창이 자기 닫힘을 가로채서(`window_manager`의
닫기 가로채기, 이미 앱이 쓰고 있는 패키지입니다) 팝업 창을 먼저 닫고
자신도 닫으면 됩니다.

### `main()`이 갈림길을 갖게 됩니다

`desktop_multi_window`는 두 번째 창을 "같은 실행 파일을 특별한 인자로
다시 실행"하는 방식으로 만듭니다. 그래서 `lib/main.dart`의 `main(List<String>
args)`가 인자를 보고 갈립니다.

- 인자가 없으면(또는 첫 인자가 팝업 표시가 아니면): 지금까지처럼 전체
  앱(`ReferenceArchiveApp`, `HomeScreen`부터 시작)을 띄웁니다.
- 인자가 팝업 창임을 가리키면: 새로 만들 **`lib/screens/board_popup_app.dart`**
  (가칭)를 띄웁니다. 이 위젯은 `AppDatabase()`를 하나 더 열고(같은 파일
  경로를 가리키므로 메인과 같은 데이터를 봅니다), 인자로 받은 `boardId`로
  `BoardScreen`을 그대로 재사용해 띄웁니다. 새 무드보드 화면을 또
  만들지 않습니다.

### 실시간 동기화

**신호를 보내는 곳**: `BoardInteractionController`가 카드를 저장할 때마다
(`addCards`/`removeCard`/드래그·크기조절이 끝나 저장할 때/정렬·분배/
`removeSelectedCards`). 지금 이 클래스는 `boardRepository`에 쓰기만 하고
아무에게도 알리지 않습니다 — **저장 직후 부를 수 있는 콜백 하나
(`onSaved`, 가칭)를 추가**해서, 그 콜백 안에서 화면(`BoardScreen`)이
"상대 창에 신호를 보낼지 말지"를 정하게 합니다. `BoardInteractionController`
자체는 `desktop_multi_window`를 몰라도 됩니다(관심사 분리 — 저장 로직과
창간 통신은 다른 layer입니다).

**신호를 받는 곳**: 양쪽 `BoardScreen`(메인에서 연 것, 팝업에서 연 것)이
전부 `DesktopMultiWindow.setMethodHandler`로 "이 판이 바뀌었다"는 신호를
듣습니다. 자기가 지금 보고 있는 판과 같은 `boardId`면, 자기 연결로
`boardRepository.getCards(boardId)`를 다시 불러 `BoardInteractionController.setCards()`로
갈아끼웁니다. **손을 대고 있는 도중(드래그 중)에는 신호를 보내지
않습니다** — `onDragEnd`/`onResizeEnd`처럼 실제로 저장이 끝난
순간에만 보냅니다. 안 그러면 상대 창이 매 프레임 다시 그리려 들어
버벅입니다.

**메시지 통로**: `DesktopMultiWindow.invokeMethod(상대창id, 'boardCardsChanged',
boardId)`. 어느 쪽이 메인이고 어느 쪽이 팝업인지는 신호를 보내는 쪽
입장에서는 중요하지 않습니다 — "지금 상대 창의 windowId"만 알면 됩니다
(메인은 팝업을 열 때 그 windowId를 기억해두고, 팝업은 자기를 연
"메인 창"의 windowId를 시작 인자로 받아둡니다).

### 팝업으로 띄우기 버튼

`board_toolbar_actions.dart`(무드보드 화면 위쪽 AppBar 버튼들)에 버튼을
하나 더 둡니다. 데스크톱에서만 보입니다(`supportsAlwaysOnTopWindow`와
같은 판정 — 폰에는 여러 창이라는 개념이 없습니다). 누르면:

1. 이미 팝업이 떠 있으면 그 팝업에 "다른 판(`boardId`)을 보여줘"라고
   신호만 보내고 끝냅니다(2번 결정 참고).
2. 없으면 `DesktopMultiWindow.createWindow(...)`로 새로 열고, 그
   windowId를 기억해둡니다.

메인 창의 이 화면은 팝업이 뜬 뒤에도 **그대로 남아 있습니다.**
팝업은 "복사본을 창으로 뽑아낸 것"이지, 메인 창에서 이 판을 치우는
것이 아닙니다 — 의뢰인이 참고하며 작업하는 동안 메인 창에서 다른
레퍼런스를 계속 정리할 수 있어야 하기 때문입니다.

## 파일 구성

- **`pubspec.yaml`** — `desktop_multi_window` 의존성 추가. **정확한
  API는 web 검색으로 얻은 정보가 최신 버전과 어긋날 수 있으므로,
  구현할 때 `flutter pub add` 이후 pub 캐시에 내려받힌 그 버전의
  `example/lib/main.dart`를 직접 읽어 실제 시그니처를 확인하고
  씁니다.** (아래 "구현 시 반드시 지킬 것" 참고)
- **`lib/main.dart`** — `main()`이 팝업/메인을 가릅니다.
- **`lib/screens/board_popup_app.dart`**(새 파일) — 팝업 창 전용 진입점.
  `AppDatabase`를 새로 열고, 받은 `boardId`로 `BoardScreen`을 띄웁니다.
- **`lib/screens/board_popup_controller.dart`**(새 파일) — 팝업 열기/
  신호 보내기/받기를 모아두는 곳. `BoardScreen`이 씁니다.
  `board_window_controller.dart`(항상 위)와 같은 결의 `ChangeNotifier`
  패턴을 따릅니다.
- **`lib/screens/board_interaction_controller.dart`** — 저장이 끝날
  때마다 부를 수 있는 콜백(`onSaved`) 추가.
- **`lib/widgets/board_toolbar_actions.dart`** — 팝업으로 띄우기 버튼
  추가.
- **`lib/screens/board_screen.dart`** — 팝업 컨트롤러를 만들고, 신호를
  받으면 카드 목록을 다시 불러오는 처리 추가.

## 구현 시 반드시 지킬 것

- **패키지 API를 문서/블로그 요약만 믿고 그대로 베끼지 않습니다.**
  이번 조사에서 pub.dev 요약과 여러 블로그 글이 서로 다른 모양의
  API(`WindowController.create` 계열 vs `DesktopMultiWindow.createWindow`
  계열)를 보여줬습니다 — 버전에 따라 다르거나, 요약 과정에서 부정확해진
  것으로 보입니다. **`flutter pub add` 후 실제로 받아진 패키지의
  `example/` 폴더 소스를 직접 읽고**, 거기 나온 그대로의 클래스/메서드
  이름을 씁니다.
- **`window_manager`(이미 있는 의존성)의 닫기 가로채기**로 "메인 창을
  닫으면 팝업도 닫힌다"를 구현합니다. 새 패키지를 추가하지 않습니다.
- **드래그/크기조절 도중에는 신호를 안 보냅니다.** `onDragUpdate`/
  `onResizeUpdate`가 아니라 `onDragEnd`/`onResizeEnd`(이미 저장이 확정된
  시점)에서만 보냅니다.
- **자기가 보낸 신호를 자기가 되받아 무한 루프에 빠지지 않게 합니다.**
  창A가 저장 → 창B에 신호 → 창B가 다시 읽어서 반영하는 것으로 끝나야
  하고, 창B가 그 반영을 "새로 저장한 것"으로 착각해 창A에 또 신호를
  보내면 안 됩니다(신호를 받아 반영할 때는 `setCards()`만 부르고,
  저장 콜백 경로를 타지 않게 합니다).

## 테스트 전략

실제로 창 두 개가 뜨고 서로 신호를 주고받는 것은 위젯 테스트로 잡을 수
없습니다("항상 위" 기능 때와 같은 사정, `board_window_controller_test.dart`
참고 — 테스트 환경에서는 플랫폼 판정 자체가 거짓이 되어 실제 창 관련
호출을 안 타므로 조용히 통과합니다).

- **`BoardInteractionController`의 `onSaved` 콜백은 단위 테스트로
  확인합니다** — 카드를 저장하는 여러 동작(추가/옮기기/크기조절/
  정렬/내리기) 각각이 콜백을 정확히 한 번 부르는지, 드래그/조절
  **도중**에는 안 부르는지.
- **실제로 팝업 창이 뜨는지, 두 창이 동기화되는지는 `flutter run -d
  windows`로 직접 확인**해야 합니다 — 이 부분은 자동화 테스트로
  검증할 수 있는 부류가 아니라는 것을 미리 밝혀둡니다(5·6단계와
  같은 사정).

## 새로 나온 개념

- **`desktop_multi_window`** — 하나의 Flutter 앱이 진짜 OS 창을 여러
  개 띄울 수 있게 해주는 패키지입니다. 각 창은 자기만의 Flutter
  엔진(화면을 그리는 독립된 실행 단위)을 갖지만, 같은 프로세스
  안에서 돕니다. 그래서 메모리(변수)는 창끼리 자동으로 안 나눠지고,
  서로 "메시지"를 보내는 방식으로만 이야기할 수 있습니다.
- **창간 메시지(inter-window messaging)** — 한 창이 다른 창에게 "이런
  일이 있었다"고 알리는 통로입니다. 메모리를 공유하지 않으니, 두
  창이 "같은 데이터를 보고 있다"고 믿으려면 한쪽이 바뀔 때마다
  서로 알려주고 다시 읽어오게 만들어야 합니다.
