# 유사도 엔진 — 설계 (6단계, 1부: 엔진 + 정렬 옵션)

- 작성일: 2026-08-31
- 상태: 브레인스토밍 완료, 사용자 검토 대기
- 관련: `CLAUDE.md` "개발 단계 — 6단계 유사도 엔진"

## 배경

`ReferenceItem.pHash`는 로컬 우선 설계 원칙(원칙 4-4, "가벼운 변경 추적")에
따라 처음부터 저장 구조에 있었지만(schemaVersion 1) 지금까지 아무도 계산하지
않았습니다. 6단계는 이걸 채우고, 태그·분류 유사도와 합쳐 "유사한 것끼리
정렬"을 만드는 것이 목표입니다.

기존 웹앱(`https://github.com/luseuss/reference-archive`)이 이미 이 기능을
구현해뒀습니다(PR #12~#14). AI 호출 없이 순수 계산으로 동작하고, 실제로
검증된 가중치가 있어서 **그대로 이식합니다.** 새로 설계하지 않습니다.

## 범위

**이번 스펙은 엔진과 정렬 옵션만 다룹니다.** 레퍼런스 상세 화면의 "비슷한
레퍼런스" 섹션(기존 웹앱의 미리보기 라이트박스에 해당)은 사용자가 명시적으로
"다음 PR로 미루자"를 골라 **이번에 포함하지 않습니다.**

## 결정된 것 (기존 웹앱에서 그대로 가져오는 것)

### 유사도 점수 (0~1)

```
score = 자카드(태그A, 태그B) × 0.35
      + (같은 카테고리 ? 0.1 : 0)
      + (같은 폴더 ? 0.1 : 0)
      + (겹치는 프로젝트가 하나라도 있으면 ? 0.1 : 0)
      + (둘 다 pHash가 있으면 (1 - 해밍거리/64) × 0.35, 없으면 0)
```

자기 자신과는 0. 최댓값은 1(태그·분류·이미지가 전부 겹치는 경우).

### dHash (perceptual hash)

이미지를 **9×8 그레이스케일로 강제 리사이즈**(가로세로 비율 무시,
`copyResize(width: 9, height: 8)`)한 뒤, 각 행에서 **가로로 인접한 픽셀의
밝기를 비교**해 8×8=64비트를 만듭니다. 밝기는
`0.299×R + 0.587×G + 0.114×B`(기존 웹앱과 동일한 가중치)입니다.

기존 웹앱은 브라우저 `<canvas>`로 계산했고, 외부 이미지의 CORS 문제로
계산이 실패할 수 있어 `try/catch`로 null 처리했습니다. 이 앱은 **이미지가
전부 로컬 파일**이라 CORS 문제 자체가 없지만, 파일이 깨졌거나 아직 안
읽혔을 가능성은 여전히 있으므로 같은 방식으로 실패하면 null을 돌려줍니다
(계산 실패 = "이 항목은 pHash 없이, 태그·분류만으로" 점수를 냅니다).

### 언제 계산하나

- **저장할 때**(새 레퍼런스 추가, 또는 기존 레퍼런스의 사진을 바꿨을 때):
  그 자리에서 계산해 저장합니다.
- **이미 있는 레퍼런스 중 `pHash`가 아직 없는 것들**: 앱을 켤 때
  화면 뒤에서 조용히 채웁니다(기존 웹앱의 `backfillPHashes`와 동일한
  개념). 저장 구조는 **안 바뀝니다** — 칼럼이 이미 있어서 채우기만
  하면 됩니다. 마이그레이션 없음.
- 이미지·유튜브 구분 없이 **`fileName`으로 저장된 파일**(유튜브는 썸네일)을
  씁니다. 이 앱은 유튜브 썸네일도 이미 로컬에 내려받아 두므로, 기존
  웹앱처럼 "유튜브면 원격 썸네일 URL, 이미지면 로컬/원격 URL"을 가리는
  로직이 필요 없습니다 — 언제나 `imageStorage.getFullPath(item.fileName)`
  하나로 통일됩니다.

### "유사한 것끼리" 정렬

기존 웹앱과 동일한 방식(완전한 클러스터링이 아닌 단순 기준점 방식):
목록에서 **가장 최근에 추가된 항목**을 기준으로 고정하고, 나머지를 그
항목과의 유사도 점수 내림차순으로 정렬합니다. 기준 항목 자체는 맨 앞에
고정됩니다.

## 이 앱에 맞게 조정하는 것

1. **핀 고정과의 관계.** 이 앱에는 기존 웹앱에 없던 "핀 고정" 기능(2단계)이
   있고, "정렬을 바꿔도 고정한 건 항상 위" 규칙이 이미 있습니다
   (`local_reference_repository.dart`의 `search()` 설명 참고). 유사도
   정렬도 이 규칙을 따릅니다: **핀 고정된 항목은 그대로 맨 위에 두고,
   고정 안 된 나머지끼리만** 유사도로 재정렬합니다. 유사도 정렬의
   "기준 항목"도 고정 안 된 항목들 중에서만 고릅니다(고정된 항목이
   기준이 되어 나머지 정렬이 자기 자신 위주로 쏠리는 것을 피하려는
   것이 아니라, 애초에 핀 고정된 항목은 정렬 대상이 아니기 때문입니다).
2. **정렬은 SQL이 아니라 Dart에서 계산합니다.** 다른 정렬 옵션(최근순 등)은
   전부 SQL `ORDER BY`로 처리되는데, 유사도는 전체 항목을 놓고 쌍끼리
   점수를 매겨야 해서 SQL로 표현할 수 없습니다. `similar`를 고르면
   저장소가 (지금 걸린 필터에 맞는) 항목을 **전부** 가져온 뒤, Dart에서
   `sortBySimilarity()`로 다시 정렬합니다. 개인용 로컬 아카이브라 항목
   수가 수백~수천 개 수준일 것으로 보고, 느려지는 것이 실제로 확인되면
   그때 최적화합니다(미리 최적화하지 않는다는 이 프로젝트 원칙).

## 파일 구성

- **`lib/utils/similarity.dart`**(새 파일, 순수 함수) —
  `jaccard`, `similarityScore`, `similarItems`, `sortBySimilarity`.
  화면·DB 없이 테스트 가능합니다.
- **`lib/services/image_hash.dart`**(새 파일) — `computeDHash(String path)`.
  파일 I/O + `image` 패키지를 쓰므로 순수 함수는 아니지만, 화면 의존은
  없습니다.
- **`lib/services/phash_backfill.dart`**(새 파일, 또는 위 파일에 합쳐도
  되는 크기면 합침) — 앱 시작 시 `pHash`가 없는 레퍼런스를 찾아
  `computeDHash`로 채우고 저장하는 조율 역할.
- **`lib/models/reference_query.dart`** — `ReferenceSortOrder`에
  `similar` 값 추가.
- **`lib/repositories/local_reference_repository.dart`** — `search()`가
  `similar` 정렬일 때 Dart 쪽에서 재정렬하도록 분기 추가.
- **레퍼런스 저장 경로**(`reference_detail_screen.dart`의 저장,
  `reference_importer.dart`의 새로 추가) — 저장 직후 `computeDHash` 호출.
- **`home_screen.dart`**(또는 앱 시작 지점) — 앱이 열릴 때 백필을 한 번
  트리거.

## 새로 나온 개념 (PR 본문에 설명 예정)

- **퍼셉추얼 해시(perceptual hash) / dHash** — 이미지를 아주 작게 축소한
  뒤 밝기 패턴만 남긴 지문 같은 값입니다. 픽셀이 완전히 같지 않아도
  "비슷하게 생긴" 이미지끼리는 비슷한 해시가 나옵니다. 해밍 거리(비트가
  다른 개수)가 가까울수록 시각적으로 비슷하다고 봅니다.
- **자카드 유사도** — 두 집합이 얼마나 겹치는지를 "교집합 ÷ 합집합"으로
  나타내는 값입니다. 태그가 5개씩 있는데 3개가 겹치면 자카드는
  3/(5+5-3)=3/7이 됩니다.
